Shadow Pancreas

A system I built as a person with type 1 diabetes, starting from my own glucose log. It combines the pre-meal glucose, that day's menu and past meals to answer "what happened in similar situations?", and summarises the answer with a local LLM.

Idea

Before a meal, the user enters the pre-meal glucose. The menu loads automatically from the date. The system finds past meals with similar nutrition content, gives a range estimate for the 2-hour post-meal value and explains it in a 3–4 sentence summary. In the evening it scans tomorrow's menu and produces advance warnings for risky meals.

The ±tolerance window and word-matching method of the prototype will be kept and used as the baseline. The main question: "How much does knowing the menu as nutrition values improve post-meal glucose prediction?"

Cleaning rules

  • Cells where post-meal, bedtime or insulin value is 0 count as missing data.
  • Column Q (header "0.125") is an average column and is not used. The AVERAGES columns on the right are derived and do not enter the model either.
  • The "EXTRA DOSE" (correction dose) at lunch and dinner becomes a separate feature. Meals with an extra dose are flagged in the analysis because they directly affect the post-meal value.
  • Each menu row is split into components: soup, main dish, rice/pasta, yogurt, salad, dessert/fruit, breakfast plate, pastry, other. A meal's nutrition is the sum of these components.
  • Parenthetical parts are parsed too. For example Avcı Soslu Piliç Izgara (Elma Dilim Patates) is two items: chicken and potato.

Dish name → nutrition values

Bread and bazlama do not look alike as words but are close as nutrition. Bread and bread kadayıf are the opposite. So similarity will be computed over the nutrition vector, not over names. The method is recipe parsing, the standard route used by dietitians. Every step can be done with free sources.

  1. Normalisation. The 571 spellings are reduced to about 200 standard dishes. For example Domates Çorba (Kaşarlı) and Kaşarlı Domates Çorbası are the same dish. TF-IDF character n-grams and embeddings work as a hybrid; ambiguous matches are confirmed by you.
  2. Standard recipe and portion. For each standard dish, ingredients per portion are written in grams. The local LLM drafts them and the roughly 50 most frequent dishes are checked by hand. The portion reference is the TÜBER (Turkey Nutrition Guide) portion sizes.
  3. Ingredient nutrient values. The primary source is TürKomp: the national database, free, 645 foods, including local foods such as tarhana, bulgur and molasses. For gaps, USDA FoodData Central: CC0 licence, 1,000 requests per hour with a free key.
  4. Nutrition vector. Carbohydrate, sugar, fibre, protein, fat and kcal per portion are computed. A glycaemic-index class (low/medium/high) is added from international GI tables. "GI-weighted carbohydrate" is derived as well. Fat and protein stay as separate features because they delay absorption.
  5. Validation. For about 30 dishes, the computed carbohydrate is compared with an independent carb count and an exchange list, and the mean absolute error is measured. Extra experiment: the difference between carbohydrate guessed directly by the LLM and carbohydrate computed by recipe parsing.
  6. Dish similarity. Three signals are combined: nutrition-vector distance (main signal), category and name embedding. Weights are chosen with validation data. The embedding is used only to link a name to a standard dish and to give a fallback estimate for dishes not in the database.

LLM comparison method

  1. 20 query JSONs are prepared from real data: different meals, pre-meal ranges, low and high cases, few-sample situations.
  2. Each candidate runs with the same system prompt and temperature 0.2. Two formats are tried: free-text summary and JSON-schema fields (placed into a template).
  3. Automatic measures:
    • numeric faithfulness: does every number in the summary exist in the context JSON?
    • forbidden-language rate: dose advice or instructions such as "do/increase/decrease",
    • language error count,
    • tokens per second and VRAM use.
  4. Blind evaluation: summaries are shuffled and model names hidden. You give each a 1–5 score for "is it understandable, is it useful to me?".
  5. Decision rule: among models with faithfulness ≥ 95% and forbidden language 0%, the highest-scoring model is chosen. If scores are close, the faster one is preferred.

Embeddings

The decision was made by measuring in Colab. Notebook and synthetic data: notebooks/embedding_karsilastirma.ipynb. Synthetic data: 127 standard dishes, 703 spelling variants and synonyms, 38 hand-marked hard pairs.

Also TF-IDF character and word baselines. T2–T4 are measured both with the name only and with "name + ingredient description".

  • Name matching: TF-IDF character n-grams + bge-m3, fused with RRF, embedding weight 0.5. Recall@5 96.6%. For ambiguous matches, the top 5 candidates are offered for confirmation.
  • Auxiliary dish-similarity signal: TR-MTEB turkish-embedding, using the "name + ingredient description" text.
  • The main similarity comes from the nutrition vector. No embedding beat the category mean (6.8 g). With names only, all models are worse than random on hard pairs (AUC < 0.5).
  • Limits: the data is synthetic and there are only 38 hard pairs, so AUC differences are rough. EmbeddingGemma and embeddingmagibu could not be run.

Because the set of dishes on the menu is fixed, embeddings can be computed once and written to a file. No embedding server is needed at run time. If necessary, the GGUF version of the winning model can run with --embeddings on a second llama-server instance; chat and embedding do not work together in the same process.

Prediction model

Case features

  • Pre-meal glucose (mg/dL), meal, injected insulin and extra dose.
  • The meal's nutrition vector (total carbohydrate, GI-weighted carbohydrate, fat, protein, fibre).
  • Previous measurement and intra-day trend, i.e. the post-meal value of the previous meal.
  • Month (season) and day of the week.

Methods to compare

CodeMethodRole
B0Always say "in range"; give the training mean as the valuesimplest baseline
B1Training median of the same mealbaseline
B2Prototype: mean post-meal value of the same meal within a pre-meal ±15 windowthe main rival
M1Weighted kNN, no dish informationmodel without food
M2Weighted kNN + nutrition vectormain model
M3Gradient boosting (LightGBM) or quantile regression + nutrition vectoralternative
  • kNN weights (how much do pre-meal glucose, carbohydrate, insulin… matter in the distance?) are chosen by random search over validation folds.
  • Prediction interval: a calibrated interval such as "80% probability of 120–190 mg/dL" via conformal prediction. The low warning comes from the lower end of this interval.
  • Ablation: no nutrition information, name matching, embedding and nutrition vector are added in turn. The answer to the main question is read from this table.

Evaluation

  • Split: By month, not random. Each month is left out in turn (6 folds). The last test month is October (40 meals) and is never used in any tuning.
  • Metrics:
    • MAE for the post-meal value,
    • missed cases and false alarms for high (>180) and low (<70), counted separately,
    • actual coverage of the prediction interval,
    • 95% confidence intervals by bootstrap.
  • Error analysis: The 10 worst predictions are examined one by one. Possible causes: extra dose, exercise, illness, exam stress, extra food eaten beside the menu.
  • Groups: Results are given separately for breakfast, lunch and dinner, for low/medium/high pre-meal ranges, and by month. If the model is clearly worse for one meal, it is visible.
  • Causality note: The insulin dose is chosen by looking at the pre-meal value and the food. The model does not say "if you take this dose, this happens"; it only shows the historical relationship.

Safety rules

  • The system never recommends a dose. Summaries only tell what happened in similar situations in the past.
  • LLM output passes two filters: numeric faithfulness (every number must exist in the context) and forbidden patterns (dose instructions, firm language such as "you must"). If output fails, a template summary is shown instead.
  • If the number of similar cases is low (e.g. <5), the summary says so clearly and widens the interval.
  • If a low risk is visible, the first sentence of the summary is about that.

Interface improvements

The base is the prototype HTML. It will be restyled and the following will be added technically:

  • The menu fills in automatically. When the date and meal are selected, dishes arrive as component cards.
  • Nutrition card: total carbohydrate of the meal, GI badge, fat and protein. A "where did these values come from?" link shows the recipe parsing.
  • Prediction band: a range instead of a single number. The 70–180 target zone and the low and high zones are shown as coloured stripes.
  • Similar-case list: the 5 nearest meals, each with why it is similar (pre-meal difference, carbohydrate difference, shared dish category).
  • LLM summary: arrives streaming, with a small label under it showing the check status.
  • Tomorrow's menu warning: when opened in the evening, the next day's risky meals are listed.
  • Model tab: baseline vs model comparison and the ablation table are shown live.
  • If the LLM is unreachable, the page keeps working with the template summary.
